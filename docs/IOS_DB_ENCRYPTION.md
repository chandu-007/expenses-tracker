# iPhone database encryption: decision document

Investigation only. No code, build file or library was changed. Written 2026-10-28 against commit `825b814` (line numbers below are that commit; `IosPlatform.kt` is being edited by another worker, so lines in the working tree may have moved by a few). `[INFERENCE]` = reasoned, not observed. `not verified` = could not be checked from here (no phone, no simulator, no iOS build was used).

## Summary and recommendation

**Recommendation: do not move the iPhone database to SQLCipher now.** Keep iOS Data Protection (what the app has), make it verifiably true on a real phone, and spend the effort on the recovery path (passphrase-protected automatic copies plus a tested restore). Revisit only for one of the reasons in section 5.

Why, in four facts:
1. **Today the file is already encrypted by the OS** (AES, per-file keys, class `CompleteUntilFirstUserAuthentication`, which is also Apple's default for app data: [Apple](https://support.apple.com/guide/security/data-protection-classes-secb010e978a/web)). It is unreadable until the first unlock after a boot. That covers the realistic threat (a lost phone with a passcode).
2. **SQLCipher with a Keychain key readable after first unlock adds almost nothing against an attacker who can read the file on a phone that has been unlocked once** (the Keychain item is readable in exactly the same state as the file). What it does add: the database file inside a Finder/iTunes or iCloud backup, and a raw file copy, become ciphertext whose key is not in the backup.
3. **The same property is the danger.** A `ThisDeviceOnly` key does not travel in any backup. Restoring a backup onto a new iPhone brings back an encrypted database whose key is gone: permanent data loss unless the owner has a separate backup file. The owner's worst outcome is data loss; this option creates a new way to get it. Android has the same failure state (`DatabaseKeyUnavailableException`, `KeyLostScreen`) and avoids the restore trap by excluding the database from every backup and device transfer, with this stated reason: "so users are never left with an unreadable file" (`androidApp/src/main/res/xml/data_extraction_rules.xml`, `AndroidManifest.xml:28-30`). The iPhone equivalent of that is option c's backup exclusion, which also removes today's backup safety net.
4. **It does not cover the rest of the data.** Bill photos and files (`Application Support/expenses/attachments`, `IosPlatform.kt:142`), the widget's published figures (App Group preferences, `IosWidget.kt:33-38`) and the export staging files stay plaintext under the same class. A password on the Finder backup ("Encrypt local backup", [Apple](https://support.apple.com/en-us/108353)) covers all of them with zero code.

If the owner still wants it (for example because `docs/PRODUCT_CONTEXT.md:216` lists FR-SEC-01 "Encrypted local database (SQLCipher or equivalent)" as a Must), section 4 is a migration that cannot lose data, and the only form I would accept is: official Zetetic `SQLCipher.swift` 4.x binary linked in Xcode, a random 256-bit raw key in the Keychain, migration started by the owner after a verified passphrase backup, old file kept. About **7 to 9 working days**, risk medium-high (section 5).

## 1. What is true today

### 1.1 How the iPhone database is opened
- One file, `Application Support/expenses/expenses.db` (`IosPlatform.kt:69-73`). The folder is created with attribute `NSFileProtectionKey = NSFileProtectionCompleteUntilFirstUserAuthentication` (`:64-66`). Nothing else sets a class (no `NSFileProtection`, `Keychain`, `SecItem` or `ExcludedFromBackup` anywhere in `shared/src/iosMain` or `iosApp`; checked with a repo-wide search).

No key, no `PRAGMA`. Class doc at `:38`: "no separate key of the app's own, so [Platform.openDriver] never reports a lost key".

### 1.3 Data Protection actually applied, and when the file is readable
- Class: `CompleteUntilFirstUserAuthentication` (class C). "Behaves in the same way as Complete Protection, except that the decrypted class key isn't removed from memory when the device is locked ... protects data from attacks that involve a reboot. This is the default class for all third-party app data not otherwise assigned" ([Apple](https://support.apple.com/guide/security/data-protection-classes-secb010e978a/web)).
- Readable: from the first unlock after each boot until the next boot, **including while the phone is locked**. Before that first unlock the open fails. `docs/IOS.md:52` already tells the owner a text that arrives before that is not captured.
- Because the code sets exactly Apple's default, the explicit attribute changes nothing today; it documents intent.
- `-wal` and `-shm`: created by SQLite inside the same folder when the first connection switches to WAL. A new file gets its class "from the app that creates it" ([Apple](https://support.apple.com/guide/security/data-protection-classes-secb010e978a/web)); with no per-file call, that is the folder's attribute or the app default, both class C. A secondary source says new files inherit the parent directory's class and that **setting a directory's class does not re-class files already inside it** ([Nutrient, iOS 17 article](https://www.nutrient.io/blog/how-to-use-ios-data-protection/); secondary, `[INFERENCE]` for this app). Consequence: nothing in the code re-classes an older `expenses.db`, but since every candidate class is C there is no gap today. It would matter if the folder were ever changed to `Complete`: old files would stay class C until each is set (`setAttributes`) and the `-wal`/`-shm` pair must be covered too.
- Not verified on a phone: the real class of `expenses.db`, `-wal`, `-shm` (`URLResourceKey.fileProtectionKey`). Data Protection is not enforced in the Simulator (stated by [Nutrient](https://www.nutrient.io/blog/how-to-use-ios-data-protection/); `[INFERENCE]` that it is true on Xcode 27), so the lead's simulator run cannot confirm it.

### 1.4 Backups
- Application Support is part of the app container and is backed up by default. Apple: "When iCloud Backup is in an enabled state, it periodically creates a backup of the user's device, including your app's data"; only `/tmp` and `Library/Caches` are excluded by default, and anything else must be marked `isExcludedFromBackup` ([Apple](https://developer.apple.com/documentation/foundation/optimizing-your-app-s-data-for-icloud-backup)). **The code never sets it** (search above), so `expenses.db`, its `-wal`/`-shm` and `attachments/` are in device backups.
- **Unencrypted Finder/iTunes backup** (Apple: "Your backup isn't encrypted by default": [Apple](https://support.apple.com/en-us/108353)): the SQLite file sits in the backup as plain SQLite. Anyone who can read that backup folder on the Mac reads every entry. The device-wide Keychain, in an unencrypted backup, is wrapped with the device's own key and cannot be restored elsewhere ([Elcomsoft](https://blog.elcomsoft.com/2020/08/extracting-and-decrypting-ios-keychain-physical-logical-and-cloud-options-explored)).
- **Encrypted Finder backup**: the whole backup, app files included, is encrypted with the owner's password; the database is as safe as that password.
- **iCloud backup**: includes the container (above). Apple states iCloud backups encrypt the information ([Apple](https://support.apple.com/en-us/108353)); whether the keys are Apple-held or end-to-end depends on Advanced Data Protection `[not verified here]`. Whether the owner's iCloud Backup is switched on is not known from the repo.
- This is the safety net the owner may be relying on today. Excluding the file removes it (option c).
- Android comparison: `allowBackup="false"` plus `data_extraction_rules.xml` / `backup_rules.xml` exclude database, preferences and files from cloud backup and device transfer, because the key lives only in that device's Keystore (`AndroidManifest.xml:28-30`; the wrapped key sits in `noBackupFilesDir`, `EncryptedDriver.kt:76`). iOS has no equivalent today.

### 1.5 Who touches the database, the key, and other plaintext
- Only the main app process opens the database. The widget (`iosApp/Widget`) and the Share extension (`iosApp/ShareExtension`) are in App Group `group.app.expenses.tracker.ios` (`project.yml:24,65,85`) but use only `UserDefaults(suiteName:)`: the Share extension says it "cannot open the app's database" (`ShareViewController.swift:4-6`), the widgets queue taps and read published strings (`TodayWidget.swift:5-7`, `QuickAddWidget.swift:5-7`). The app drains those queues into the database when it runs (`IosWidget.kt:82-169`). No extension holds a Keychain item or a database key; the database is not in the shared container.
- Code paths that open the database possibly while the phone is **locked** (after a first unlock): `BGAppRefreshTask` (`Notifications.swift:24-47` -> `IosNotifications.checkAsync` -> `IosCore.get(h).container`), the Shortcuts "Capture bank message"/"Add expense" intents (`IosCapture.kt:28-63`, run in the background; `IOS.md:91` "Allow Running When Locked"), notification action buttons (`IosNotifications.kt:132,169`), scheduled automatic copy (`IosNotifications.kt:119` -> `IosAutoExport.runIfDue`).
- Other plaintext that no database option protects: bill photos (`attachments/`), the widget's published figures when neither Hide amounts nor App lock is on (`IosWidget.kt:36-38`), staging files for the share sheet in `NSTemporaryDirectory()/export` (`IosSystem.kt:81`), the `node_id` default.
- A parallel, uncommitted change by another worker adds a Keychain item for the automatic-copy key (`IosSecretStore.kt`, `CryptoServices.swift` `secretPut/secretGet/secretDelete`, `AfterFirstUnlockThisDeviceOnly`). That machinery can be reused for a database key, with one change: its `secretGet` returns `nil` for both "not there" and "not readable yet", which a database key cannot afford (section 4).

## 2. Options

### 2a. SQLCipher for Kotlin/Native
**What exists (verified unless marked):**
- SQLDelight 2.4.0's native driver has no SQLCipher variant. SQLiter 1.3.3 does carry the hooks: `DatabaseConfiguration.Encryption(key, rekey)`, `setCipherKey`, `resetCipherKey` (strings in the cached klib; source above). The key is applied right after the connection opens as `PRAGMA key = '<key>';` (quotes doubled), before `PRAGMA journal_mode` and before migration. The `NO_VERSION_CHECK` constant exists "for converting a clear text db to an encrypted db" (same source). SQLiter does **not** contain SQLCipher: its maintainer says so ([issue #94](https://github.com/touchlab/SQLiter/issues/94): "if you link to sqlite on iOS, you can pass in an encryption key but it won't matter. You need to bundle and link to SQLCipher").
- Danger: with the system SQLite linked, `PRAGMA key` does not fail and the file may not be encrypted at all (Touchlab saw the iOS copy react to the pragma; [Touchlab](https://dev.to/touchlab/multiplatform-encryption-with-sqldelight-and-sqlcipher-5do4)). So the app must assert `PRAGMA cipher_version` is non-empty and `PRAGMA cipher_status` is 1 (SQLCipher >= 4.12) before using the connection.
- A community artifact exists: `io.github.yet300:sqlcipher-driver` ([repo](https://github.com/yet300/SQLCipher)): Apache-2.0, stock SQLiter driver linked against a SQLCipher 4.16.0 static archive built by its own script and committed as binary `libsqlcipher.a` in git; version 0.1.0, 0 stars, one author, created 2026 (repo metadata read; whether it is on Maven Central not checked). It passes the key as a hex passphrase (PBKDF2 on every connection) rather than a raw key. I would not put the only copy of the owner's data under an unreviewed binary blob. Its build script is a useful recipe (`-DSQLITE_ENABLE_FTS5`, `SQLCIPHER_CRYPTO_CC`, `SQLITE_TEMP_STORE=3`).
- **Official binary, inspected here:** `https://github.com/sqlcipher/SQLCipher.swift/releases/download/4.20.0/SQLCipher.xcframework.zip` (Zetetic's package; SHA-256 `1505174f...f012d747` equals `Package.swift`'s checksum). The `ios-arm64` slice: SQLite **3.54.1**, SQLCipher 4.20.0; compile options include `ENABLE_FTS5`, `HAS_CODEC`, `TEMP_STORE=2`, `THREADSAFE=1`; exports `sqlite3_open_v2`, `sqlite3_key`; contains `sqlcipher_export`, `cipher_status`, `cipher_integrity_check` and the `trigram` tokenizer; links Security and CoreFoundation only (CommonCrypto provider). **It is a dynamic framework** (`Mach-O ... dynamically linked shared library`), so it must be embedded. Its own `PrivacyInfo.xcprivacy` declares DiskSpace `E174.1` and FileTimestamp `C617.1`/`3B52.1` (the app's manifest today lists only UserDefaults, file timestamps, boot time: `IOS.md:83`). Latest tags 4.19.0 and 4.20.0 are one day old; 5.0.0-beta.1 exists and is explicitly "NOT COMPATIBLE with SQLCipher 4 and earlier by default": do not use 5.x ([releases](https://github.com/sqlcipher/SQLCipher.swift/releases)).
- CocoaPods: the `SQLCipher` pod path was removed upstream in 4.11.0 ([changelog](https://raw.githubusercontent.com/sqlcipher/sqlcipher/master/CHANGELOG.md)); this repo has no CocoaPods plugin anyway. Kotlin's SwiftPM import (`swiftPMDependencies`) is Alpha and documented for KGP **2.5.0-Beta2** ([Kotlin docs](https://kotlinlang.org/docs/multiplatform/multiplatform-spm-import.html)); this repo is on 2.4.20, so it is not available, and not needed: SQLiter calls plain `sqlite3_*` symbols, so the binding can be done where the app is linked.

**Exact changes in this repo:**
1. `iosApp/project.yml`: add `packages: SQLCipher: {url: https://github.com/sqlcipher/SQLCipher.swift, exactVersion: 4.20.0}` (XcodeGen syntax `[INFERENCE]`, not tried) and a `package: SQLCipher` dependency on the `Expenses` target (embedded, because it is dynamic); **remove `-lsqlite3` from `OTHER_LDFLAGS`** (line 57) so exactly one library exports `sqlite3_*`. `-lz` stays. `ExpensesTests` links the app as host, so it needs no change `[INFERENCE]`.
2. Gradle: nothing to add for linking. `implementation("co.touchlab:sqliter-driver:1.3.3")` in `iosMain` is needed only if the migration uses SQLiter's connection API directly (it is a transitive dependency today).
3. Kotlin (iosMain): `openDriver()` passes `encryptionConfig = Encryption(key = "x'<64 hex>'")` through the existing `onConfiguration` hook (`IosPlatform.kt:75`), then runs the `cipher_status` assertion. `PRAGMA key = "x'<64 hex>'"` is SQLCipher's raw-key form, no PBKDF2 ([SQLCipher API](https://www.zetetic.net/sqlcipher/sqlcipher-api/)); Android already uses it (`EncryptedDriver.kt:56-64`). Passing it through SQLiter's quote-escaping yields the same string value `[INFERENCE]`, to be proven by a test.
4. Swift host: Keychain access with a three-way result (section 4).
5. Open-source notices: see "Licence" below.

**Schema / SQLite requirements.** Upserts `ON CONFLICT ... DO UPDATE` need SQLite >= 3.24 (`core/storage/build.gradle.kts:48`; used e.g. `Schema.sq:425-427`). FTS5 with `tokenize='trigram'` over an external-content table (`Schema.sq:380`) needs >= 3.34 and the FTS5 module compiled in, plus the `automerge`/`crisismerge`/`merge` commands (`FtsTuning.kt`). The official 4.20.0 iOS binary meets all of it (above). Android already runs the same schema on `sqlcipher-android` 4.19.1 (`libs.versions.toml:12,39`). `AUTOINCREMENT` on `entry.seq` (`Schema.sq:104`) makes `sqlite_sequence` part of the data and the FTS index points at `seq`, so a copy must preserve `seq` values (section 4, V3/V5). A custom SQLCipher build without `-DSQLITE_ENABLE_FTS5` would fail on `CREATE VIRTUAL TABLE`; Zetetic's source-integration flag list does not include it ([Apple integration page](https://www.zetetic.net/sqlcipher/sqlcipher-apple-community/)), so never build from the amalgamation with default flags.

**Licence (4.x Community).** BSD-style; "you must include our BSD-style license and copyright statements prominently in the application and documentation": the copyright line "Copyright (c) 2008-2026, ZETETIC, LLC", the full licence text, and the notices of dependencies, in a user-accessible place such as an About / Open Source Licenses screen or a linked page ([Zetetic](https://www.zetetic.net/sqlcipher/community/)). Forks must not use the bare name "SQLCipher". **Repo gap that already exists:** Android ships SQLCipher today and I found no licences/third-party screen (searched `shared/src/commonMain`, `docs/PRIVACY_POLICY.md`, `androidApp/src/main`; `PRIVACY_POLICY.md:11` even says the app contains no third-party software that collects data, which is true but is not an attribution). Needed regardless of what is decided here. The Community build has no value-level encryption or encrypted virtual tables (those are Commercial/Enterprise: [SQLCipher API](https://www.zetetic.net/sqlcipher/sqlcipher-api/)).

**Also known:** if the file ever moves into the App Group (so a widget can read it), a SQLCipher file looks like random bytes, and iOS then kills the app (`0xdead10cc`) when it backgrounds holding a lock on a WAL database in a shared container; the documented workaround is `PRAGMA cipher_plaintext_header_size = 32` ([SQLCipher API](https://www.zetetic.net/sqlcipher/sqlcipher-api/), TN2408 cited there). Not an issue while the file stays in the app's own container.

**Effort/risk:** section 5. **Protects against:** file at rest in backups and raw copies, forensic images taken without the Keychain. **Does not:** an attacker on an AFU phone, jailbreak/root, the attachments, the widget cache, the owner's own plain copies.

### 2b. Encrypting individual columns (merchant, note, amounts)
- Search: `entry_fts` indexes `merchant` and `note` text with a trigram tokenizer, content table `entry` (`Schema.sq:380`). An FTS index over ciphertext finds nothing; an index over plaintext leaks the text into `entry_fts_*` shadow tables, defeating the point. The substring search (`searchEntries`, `searchShort` with `LIKE`) would have to decrypt every row in Kotlin: seconds on a 100,000-row ledger `[INFERENCE]`, versus 8-15 ms for the indexed search measured on an Android 8 emulator (`FtsTuning.kt:12-14`).
- Amounts: `amount_minor` is used in SQL `SUM`/`GROUP BY` for balances, reports, budgets and per-account sums (`entry_account_sums` index in `SchemaUpgrade.kt:26`; balance query in `Schema.sq`). Encrypted amounts mean every report and balance moves from SQL into app code; indexes on amounts, `ORDER BY`, range filters (`min_rupees`/`max_rupees` in saved searches) stop working.
- Everything else stays readable (dates, kinds, category and account ids, names of accounts, people, bills, SMS bodies in `inbox`/`entry_origin`/`bill`), so the "protection" is partial and the schema grows a key-management problem per column.
- Verdict: poor fit; large rewrite of stores and tests for less protection than whole-file encryption. Not recommended in any form.

### 2c. `NSFileProtectionComplete`, and excluding the database from backups
- **Complete** (class A): class key discarded shortly after lock (10 seconds with "Require Passcode: Immediately"; [Apple](https://support.apple.com/guide/security/data-protection-classes-secb010e978a/web)); the file cannot be read or written while locked ([Apple doc](https://developer.apple.com/documentation/foundation/fileprotectiontype/complete?language=objc)). Real gain: closes the "locked phone, booted and unlocked once" gap (row 2 of the table) without any key management.
- **What breaks while the phone is locked** (all open the database): the Shortcuts capture automation (the app's only automatic bank-message path on iPhone), the background refresh that decides reminders and records widget quick-adds, scheduled automatic copies, notification buttons that write ("Mark paid", snooze). A text that arrives while locked would no longer be captured at all, not just "before the first unlock". Widgets and the Share extension keep working (they use App Group preferences, which have their own class: `[INFERENCE]` class C by default, not checked). An already open SQLite connection that is hit by the lock in the middle of a write can fail with I/O errors `[INFERENCE]`; the "unless open" class (B) only helps files that were opened before the lock, so it does not rescue a background launch that must open the file itself.
- Apple's own table says apps using background refresh should use the after-first-unlock classes for items needed in the background ([Apple, keychain classes](https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web)); the same reasoning applies to the file.
- **Exclude from backups** (`isExcludedFromBackup` on the `expenses` folder; it is "guidance", must be re-set whenever a file is saved because file operations can reset it, and is not a guarantee: [Apple](https://developer.apple.com/documentation/foundation/optimizing-your-app-s-data-for-icloud-backup)). Effect: the file leaves Finder and iCloud backups; a restore to a new phone, or after a reset, brings back **no data at all**. The only copies are the owner's exports. It removes the exposure in rows 5-7 and a safety net at the same time. I would not do this until passphrase-protected automatic copies are shipped and a restore has been tried.
- Effort: Complete is one line plus per-file `setAttributes` for existing files (0.5 day) but the lock-screen features above must be accepted as lost; exclusion is 0.5 day.

### 2d. Do nothing (keep class C)
Zero change, zero new failure modes. Gaps are the backup rows and AFU rows of section 3. Cheap, no-code mitigations: turn on "Encrypt local backup" in Finder; keep iCloud Backup on only with Advanced Data Protection if wanted `[not verified here]`; make the automatic copies passphrase-protected (separate work in progress); turn on Hide amounts (stops the widget figures being written, `IosWidget.kt:36-38`).

## 3. Threat model

Legend: **P** protected, **-** not protected, **~** partly, **n/a** no effect. Columns: **a** SQLCipher, raw key in Keychain `AfterFirstUnlockThisDeviceOnly`; **b** per-column encryption (same key store); **c** `Complete` + excluded from backups; **d** nothing (class C).

| Threat | a | b | c | d | Notes |
|---|---|---|---|---|---|
| Lost phone, passcode set, never unlocked since boot (BFU) | P | P | P | P | Already P in d: class C keys do not exist before first unlock ([Apple](https://support.apple.com/guide/security/data-protection-classes-secb010e978a/web)). |
| Lost/stolen phone, locked, but unlocked once since boot (AFU), attacker with an extraction tool | - | - | P | - | `[INFERENCE]` about tooling, no source read. a/b: the Keychain item is available in the same AFU state as the file (Keychain class table: [Apple](https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web); AFU yields far more Keychain items than BFU: [Elcomsoft](https://blog.elcomsoft.com/2020/08/extracting-and-decrypting-ios-keychain-physical-logical-and-cloud-options-explored)). c closes it, at the cost of the lock-screen features. |
| Stolen phone and unlocked / passcode known | - | - | - | - | App lock (Face ID gate) is a UI gate, not encryption. |
| Jailbroken phone or root-level forensic access to a running AFU phone | - | - | ~ | - | Keychain dump tools read AFU items on the device. c helps only while locked. |
| Unencrypted Finder/iTunes backup on the Mac | ~ | ~ | ~ | - | a: database file is ciphertext, key not restorable elsewhere; **but** `attachments/` and widget prefs are still plain. b: only merchant/note unreadable. c: database absent from the backup; attachments still there unless also excluded. |
| Encrypted Finder backup | P | P | P | P | Password-protected by Apple already. a adds nothing and, with a `ThisDeviceOnly` key, loses the key on restore to another phone. |
| iCloud backup | ~ | ~ | ~ | ~ | Encrypted at Apple (key custody `[not verified]`). a: same as unencrypted-backup row for a restore onto another device. c: no cloud copy at all. |
| Malware / another app on a non-jailbroken phone | n/a | n/a | n/a | n/a | iOS sandbox; the container is not readable by other apps. |
| Owner's own automatic copies in iCloud Drive / a Files folder | n/a | n/a | n/a | n/a | Independent of the live file: a plain `.expbak` there is the weakest link whatever is chosen here. The separate passphrase-protected-copy feature (`EXPENC3`, `AutoCopyProtection.kt`) is the control for this row. |
| **Data loss:** restore to a new phone from Finder/iCloud backup | **loss** | **loss** | **loss** (no file) | P | a/b: file returns, key does not (Keychain `ThisDeviceOnly` is UID-wrapped in every backup type: [Elcomsoft](https://blog.elcomsoft.com/2020/08/extracting-and-decrypting-ios-keychain-physical-logical-and-cloud-options-explored)). Only a separate `.expbak`/`EXPENC2` file saves the owner. |
| **Data loss:** delete the app and reinstall | **loss of key side** | same | same | loss of file | Database goes with the app, the Keychain item stays; a fresh install must replace a stale key (section 4). |

Honest summary of a: it helps in the backup/raw-copy rows and at BFU-like moments that class C already covers; it does nothing in the AFU/jailbreak/unlocked rows; and it turns the restore-to-new-phone row from "works" into "total loss without a separate backup".

## 4. Migration plan that cannot lose data (only if the owner chooses a)

**Principles.** The migration is started by the owner (More > Privacy > "Encrypt this iPhone's database"), never silently on update. Whether a file is plain or encrypted is decided by its first 16 bytes (`SQLite format 3\0` = plain; anything else = SQLCipher), not by a flag, so an interrupted run can never confuse the open path. The old plain file is never deleted by the migration. A missing/unreadable key never causes a new empty database to be created.

**Preconditions (screen shows each as a tick):** unlocked, app in front; free space >= 3x the database size; no background run in progress (take `IosCore`'s lock); a passphrase-protected backup made through the existing flow in this session ("Backup saved and checked ...", `LedgerViewModel.kt:2678-2681`; `EXPENC2`, `BackupSeal.kt:22-36`) and saved to Files or iCloud Drive, off the phone's private folder. Note `BACKUP_FORMAT.md` payload leaves out deleted entries and `op_log`, so the backup is a recovery path, not the migration source and not the verification reference.

**Steps (state kept in an atomically written `migration.state` file in `Application Support/expenses`; every step idempotent):**
1. *Stage key.* Generate 32 random bytes (`SecRandomCopyBytes`), write Keychain item `db_key_pending` (`AfterFirstUnlockThisDeviceOnly`), read it back and compare. Nothing is deleted first.
2. *Quiesce.* `container.close()`; on a SQLiter connection with `NO_VERSION_CHECK` and no key: `PRAGMA wal_checkpoint(TRUNCATE)`; close; assert `expenses.db-wal` is 0 bytes or absent.
3. *Export into a new file.* On a plain connection: `ATTACH DATABASE '<dir>/expenses.enc.tmp' AS enc KEY "x'<hex>'"`; `SELECT sqlcipher_export('enc')` ([Zetetic](https://www.zetetic.net/sqlcipher/sqlcipher-api/): duplicates "the schema, triggers, virtual tables, and all data"); `PRAGMA enc.user_version = <source user_version>` (export "does not alter the `user_version`", and SQLiter/SQLDelight use it to decide create vs migrate, so a copy left at 0 would run `Schema.create` over an existing schema); `DETACH`. `ATTACH` cannot run inside a transaction `[INFERENCE]`, so use SQLiter's low-level connection, not `SqlDriver.transaction`.
4. *Verify, new against old (all must hold, else delete `.tmp`, stop, tell the owner, nothing changed):*
   - V1 open `.tmp` with the key on a fresh connection: `cipher_version` non-empty, `cipher_status = 1`, `PRAGMA cipher_integrity_check` returns no rows, `PRAGMA integrity_check = ok`.
   - V2 `SELECT type, name, tbl_name, sql FROM sqlite_schema ORDER BY type, name` identical text in both; `user_version` equal.
   - V3 row count per table for every table in `sqlite_schema` incl. FTS5 shadow tables and `sqlite_sequence`; counts equal and `sqlite_sequence.seq` for `entry` equal.
   - V4 content hash: for each ordinary table, stream `SELECT quote(c1)||char(31)||quote(c2)... FROM t ORDER BY rowid` (primary key for `WITHOUT ROWID` `entry_tag`) into the app's pure-Kotlin `Sha256` (`Sha256.kt`); one digest per table; then SHA-256 over the sorted `table:digest` lines. Old and new digests must be equal. Skip FTS5 shadow tables (internal segment layout may differ).
   - V5 FTS: `INSERT INTO entry_fts(entry_fts) VALUES('integrity-check')` on the new file; for 20 sample 3+ character words taken from existing merchants/notes, `count(*)` of `entry_fts MATCH` equal in both. If only V5 fails, `'rebuild'` once (as `BulkLoad.kt` does), then re-check.
   - V6 show the owner counts and per-currency sums from both files side by side before confirming.
5. *Swap, never leaving zero files.* (a) rename `-wal`/`-shm` of the old file aside (a stale WAL paired with another database file could be replayed `[INFERENCE]`); (b) copy `expenses.db` to `expenses.db.plain-<date>` and fsync; (c) replace `expenses.db` with `.tmp` by one atomic rename (`replaceItemAtURL`/`rename(2)`); (d) write Keychain `db_key` = pending bytes (compare), keep `db_key_pending` until the first good open; (e) state := `ENCRYPTED, launches=0`.
6. *Confirm over two launches.* After each launch that opens with the key, asserts `cipher_status`, runs `SELECT count(*) FROM entry` equal to the count recorded in V3, `launches++`. At 2, state := `CONFIRMED`, `db_key_pending` removed. The `.plain-<date>` file stays until the owner presses "Delete the old unencrypted copy" (explain: copies already in earlier backups cannot be recalled). Photos are not part of this and remain plain.
7. *Automatic rollback.* If a launch with state `ENCRYPTED` cannot open the new file for a reason other than "key unavailable right now" (`NOTADB`, `cipher_status != 1`, count mismatch): close, rename `expenses.db` to `expenses.db.enc-failed-<ts>`, rename the `.plain-` copy back, state := `ROLLED_BACK` (no automatic retry), show a notice. Never delete either file.

**Killed mid-migration (recovery on next launch, by state + header):** during 1-4: `expenses.db` untouched and plain; delete `.tmp`, resume at 1. During 5(a)-(b): same. Between (c) and (d): header is encrypted, `db_key` missing, `db_key_pending` present: open with it, promote, continue. After (d): normal. At no point is `expenses.db` absent: (c) is a replacement, not delete-then-move.

**Open path after migration** (`openDriver`): read header. Plain -> open as today. Encrypted -> read Keychain with a three-way result: *found* (open), *not found* (throw `DatabaseKeyUnavailableException` -> existing KeyLost screen; **do not** create a database; the Android rule "a key is only created together with a brand-new database", `EncryptedDriver.kt:30-31,89`), *unavailable now* (`errSecInteractionNotAllowed`, before first unlock: return a "locked" outcome and retry on the next foreground; this is **not** KeyLost, and nothing is created or rolled back). The sibling `secretGet` collapses the last two into `nil` and must not be reused unchanged. SQLCipher cannot tell a wrong key from a corrupt file (both fail the page HMAC), so message both. A brand-new install (no file) creates the key and the database together; a stale Keychain item from an earlier install is replaced, never read.
- KeyLost on iOS must not delete: the current `startFresh` -> `resetDatabase()` removes files (`IosPlatform.kt:77-79`); for an encrypted file it should move them aside (`expenses.db.unreadable-<ts>`) and delete no Keychain item, because a restored key could make them readable again.

**Keychain lifecycle.**
| Event | What happens | Consequence |
|---|---|---|
| App deleted | Keychain item survives (stated in the sibling's code comment, `IosSecretStore.kt:6-7`, and widely documented; `[not verified here]`); database file goes | Fresh install: no file -> new key replaces the stale item. |
| Reinstall over the old app (free-signing refresh, `IOS.md:72-80`) | Container and Keychain both stay if the application identifier (Team ID + bundle id `app.expenses.tracker.ios`) is unchanged, which the documented flow keeps ("same bundle id, so the data stays") | `[INFERENCE]`: the default keychain access group is Team ID + bundle id. **Must be tested on the real phone, including after the profile changes** (section 4 test 11). A different Apple ID/team would orphan the key. |
| Backup restored to the same phone | Container restored; `ThisDeviceOnly` item restorable to the same device ([Elcomsoft](https://blog.elcomsoft.com/2020/08/extracting-and-decrypting-ios-keychain-physical-logical-and-cloud-options-explored)) | Works. |
| Restore / new phone / erase and restore from iCloud | File returns, key does not | KeyLost; owner restores from `EXPENC2` file. This is the principal risk. |
| Passcode removed | `ThisDeviceOnly` After-first-unlock items are not tied to the passcode (only `WhenPasscodeSet...` items are) | Fine. |
| Alternative: non-`ThisDeviceOnly` or `kSecAttrSynchronizable` | Travels in encrypted Finder backups / iCloud Keychain ([Apple](https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web)) | Would remove the new-phone loss, but puts the key in iCloud Keychain and depends on the owner's account state `[not verified]`; owner decision, not in the base plan. |

**Test plan.**
- *Simulator / unit (Kotlin/Native + XCTest):* (1) migrate a synthetic ledger: 100,000 entries, deleted rows, NULLs, 64-bit extremes, non-ASCII merchants, tags, splits, attachments rows, `AUTOINCREMENT` gaps; digests V4 equal; (2) fault injection: throw after every numbered step, relaunch, end state is a readable database with the same digests; (3) wrong key, missing key + encrypted header, header-only corrupt file: KeyLost, files untouched; (4) simulated `errSecInteractionNotAllowed`: no file created, no rollback; (5) negative: build variant linked with `-lsqlite3` and no SQLCipher: `cipher_version` empty -> refuses to open; (6) `strings` on `expenses.db` and `-wal` after writes: no merchant text, first 16 bytes not `SQLite format 3`; (7) FTS parity: the `FilteredSearchTest`/`SearchOrderTest` queries run on the native driver (they are JVM-only today); (8) WAL checkpoint, vacuum and `FtsTuning.mergeStep` still work; (9) save latency and cold open vs plain (Android reference: 0.32 ms median per save in WAL, `EncryptedDriver.kt:27-28`).
- *Real iPhone only (the simulator does not enforce Data Protection or real Keychain classes):* (10) file protection class of `expenses.db`, `-wal`, `-shm` read back; (11) Keychain item survives (a) install-over with a freshly renewed profile, (b) delete and reinstall; (12) reboot, do not unlock, trigger the Shortcuts intent and a background refresh: no crash, no new database; then unlock: works; (13) lock-screen capture works after first unlock; (14) Finder backup (plain and encrypted) and iCloud restore onto a **second device**: expect KeyLost, then restore from the `EXPENC2` file succeeds with equal counts; (15) 7-day-profile refresh via `tools/ios_refresh.sh` keeps data.

## 5. Effort, risk, recommendation

Effort for the recommended form of a (days, one developer, includes tests and device runs):
| Task | Days |
|---|---|
| Link `SQLCipher.swift` (XcodeGen package, embed, drop `-lsqlite3`), prove one `sqlite3` provider, privacy manifest, K/N link cycles at ~12 GB heap (`IOS.md:63`) | 1 |
| Keychain host API with three-way result, `IosDbKey`, open path by header, `cipher_status` assertion, KeyLost on iOS that never deletes | 1.5 |
| Migration state machine, export, verification (V1-V6), swap, rollback, recovery | 2.5 |
| Owner UI (preconditions, progress, results, delete-old-copy), wording, privacy policy and `IOS.md` update | 1 |
| Licences/About screen with SQLCipher notice (needed for Android today too) | 0.5 |
| Tests 1-9 and real-device tests 10-15 (spare device needed for 14) | 2 |
| **Total** | **7 to 9** |

Risk: **medium-high.** Largest items: a silent link mistake leaving the system SQLite in place (mitigated by the assertion and test 5); an interrupted or wrong migration (mitigated by header-driven open, copy-keeps-original, atomic swap); the restore-to-new-phone key loss (not mitigable by code, only by the owner's separate backup); SQLCipher major-version change (5.x is incompatible; pin 4.x); one more dynamic framework in an app that is re-signed every 7 days (embedded frameworks are re-signed with the app; `[INFERENCE]` fine, test 15). Kotlin/Native `PRAGMA` handling of the raw key string through SQLiter is unproven (test 1).

**RECOMMENDATION: not now.** Rationale: the realistic threat is covered by class C; encryption in a form that survives restore to a new phone needs either iCloud Keychain custody or reliance on the owner's own backup discipline; the main extra protection (backups) is cheaper to get with an encrypted Finder backup and also covers the photos; and the downside of a lost key is the one outcome the owner has ruled out. If FR-SEC-01 must be met literally on iPhone, do option a only in the form above, and only after (i) passphrase-protected automatic copies exist, (ii) one full restore from such a copy onto a second device has been done, (iii) the owner accepts the KeyLost-on-new-phone behaviour in writing.

**What would change the recommendation:**
- An App Store release or any store/privacy wording that claims "encrypted at rest" on iPhone (the Play listing already says it for Android: `docs/PLAY_LISTING.md:31`), or a compliance reading that Data Protection is not "SQLCipher or equivalent" (`PRODUCT_CONTEXT.md:216`).
- The owner routinely makes unencrypted Finder backups, or iCloud Backup is on without Advanced Data Protection, and will not change that.
- A second person's data in the app, or a plan to move the database into the App Group (then plaintext-header handling, `0xdead10cc`, and a fresh decision are needed).
- iCloud-Keychain-synchronised key custody judged acceptable (removes the new-phone loss).
- A real device test showing the file or its `-wal`/`-shm` is **not** class C (then fix the class first; that is a one-line change).
- SQLCipher 5.x going stable with a published migration path (re-evaluate format and effort then).
