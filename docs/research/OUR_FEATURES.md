# Our app: feature inventory (verified against code, version 0.7.1; rows and notes marked 0.8.0 were updated for that release); the rows and notes marked "after 0.8.0" describe the own-account transfer, starter category and subscription work that shipped as version 0.9.0 (section 19)

Scope: Kotlin Multiplatform app. Android (`androidApp`, minSdk 26, versionCode 29, Play and APK builds) and iPhone (`iosApp`, 0.7.1 build 26, iOS 17+, free-signed test build only). Shared UI and logic: `:shared` commonMain; `core/{domain,storage,parsers}`.

Maturity key (from the docs and the test folders; nothing here was run by me):
- **Emu** = exercised by Android instrumented tests on an API 26 emulator (`androidApp/src/androidTest`).
- **Sim** = exercised on the iOS simulator only (`iosApp/Tests`, `iosApp/UITests`).
- **Unit** = JVM/common unit tests only.
- **No device** = never run on a real phone. The docs (`REAL_DEVICE_CHECKLIST.md`, `IOS.md`) say real-device checks are mostly pending. The only real-device facts in the docs are the owner's iPhone install and real HDFC statement/message samples. Treat every row below as "not verified on a real device" unless it says otherwise.

"Both" = Android and iPhone share the code (commonMain), so the feature exists on both, but it is tested where the Maturity column says.

## 19. Two own-account transfer texts: what the app derives (after 0.8.0, 2026-10-29)

The owner's two real HDFC Bank texts for one move between his two accounts, here with invented digits (1234 the source account, 5678 the destination) and read through the real code (`CapturePipelineTest`, `OwnTransferTextsTest`; run output is printed by the first):

- SMS 1, "Amt Deducted! Rs.45,250.75 from your HDFC Bank A/c XX1234 for Money Transfer via HDFC Bank Online Banking. Not you?Call ...": a debit of 4,525,075 paise from the account ending 1234. **Merchant: none** (the text names nobody), so the card and an added entry are titled with the bank, "HDFC Bank". **Category: none**: no merchant-table match, nothing learned (a learned category needs a payee name), no history (also needs a payee), and a person's own rule matches only if its words occur in the text. As a transfer it has no category at all (transfers are neither spending nor income). Unchanged by this work, apart from the new "might be a transfer to your other account" note.
- SMS 2, "Update! INR 45,250.75 deposited in HDFC Bank A/c XX5678 on 29-OCT-26 for XXXXXXXXXX1234-TPT-Holiday Fund Remembe-SAMPLE TRADERS PRIVATE LIMITED.Avl bal INR 3,21,654.32. ...": a credit of 4,525,075 paise into 5678 (the balance "Avl bal INR 3,21,654.32" is not taken as the amount), dated 29 Oct 2026, naming account 1234 (`counterLast4`). **Merchant before: none ("HDFC Bank")**; **after: "Holiday Fund Remembe"** (the note typed by the sender in the TPT narration, cut by the bank at 20 characters; the beneficiary part "SAMPLE TRADERS PRIVATE LIMITED" is the account holder's name and is not used because the note is the more useful title). **Category: none**: a captured credit carries no category suggestion (suggestions are for debits), and the note is no known merchant; if it were a debit, the starter table and `PERSON` rule would still say nothing ("Holiday Fund Remembe" has no `@`, so it is not read as a person's UPI address).
- **What the app showed before**: an expense out of 1234 and income into 5678, each titled "HDFC Bank", the overall money flow overstated by 45,250.75 on both sides. **After**: one card "Transfer from Bank to Savings ₹45,250.75" (when both accounts carry their last four digits), Add makes one transfer (`OwnTransferUiTest`).
- Where the title and category come from, in order (`LedgerViewModel.inboxRows`, `CategorySuggest.suggest`): the person's own rule (words in the payee or text), what they chose last time for the payee, their earlier entries for the payee, the starter merchant table (best home first, then the coarse category), the bank's own charge words, then "a payment to a person" (Other) for a UPI address that looks like a person. The title is the name given by the person for that address, else the starter table's clean name, else the payee as read, else (after 0.8.0) the clean name in a bank narration, else the bank.
- Not verifiable here: how a real HDFC text for another beneficiary, an NEFT to another bank, or another bank's own-account wording reads (only HDFC's public sample shapes were used).
